# Dogfood Gaps

- 2026-05-01: **`rt refactor rename` does not rename the source file on disk** when a class is renamed. Reproducer: `rt refactor rename "RoslynTools.Core.MakeSealedCore" "MakeSealedService" --solution RoslynTools.slnx` — class declaration and call sites correctly become `MakeSealedService`, but the file remains `src/RoslynTools/Core/MakeSealedCore.cs`. Result: file basename and contained type name diverge (StyleCop SA1649). Fix: after renaming a class via Renamer, if the source file's basename equals the old type name, also move the document to the new basename via `Solution.WithDocumentFilePath` (or analogous Roslyn API). Opt-out via `--keep-file-name`. Surfaced during Core/ reorg tracer-bullet session 2026-05-01.
  - **FIXED 2026-05-01 (extended for batch)**: `RenameService` extracted a private `RenameOneAsync(sln, symbol, newName, kind, dryRun)` that both `ExecuteSingleAsync` and `ExecuteBatchAsync` now call, so `--csv` batch renames also rename the source file when basename matches the old type name. Test: `BatchRename_renames_each_source_file_when_basename_matches_old_name` in `RenameIntegrationTests.cs`.
- 2026-05-01: **`rt refactor move --type` doesn't update consumers of co-located types in the moved file.** Reproducer: a file with `class Target` AND `record CompanionDto(...)` in `namespace Foo;`. `rt refactor move --type Foo.Target --to-namespace Bar --move-file` correctly moves both types' namespace (because they share the file-scoped namespace declaration) and adds `using Foo;` to the moved file's siblings, but consumers that referenced `CompanionDto` unqualified (via `using Foo;`) don't get a new `using Bar;`. Root cause: `ApplyReferenceUsingsAsync` only walked `SymbolFinder.FindReferencesAsync(sym)` for the named target type; references to co-located types in the same file were ignored.
  - **FIXED 2026-05-01**: `MoveCore.ExecuteSingleTypeMoveAsync` now calls `CollectCoLocatedTypesAsync` (semantic walk over `BaseTypeDeclarationSyntax` in `sym`'s declaring tree, deduped by `SymbolEqualityComparer`) and runs `FindReferencesAsync` for every co-located type. `Task.WhenAll` parallelises the lookups; results flatten into one reference list passed to `ApplyReferenceUsingsAsync`. Test: `SingleTypeMove_updates_consumers_of_co_located_types_in_the_moved_file` in `MoveIntegrationTests.cs`. Surfaced when batching the Core/→Services/ refactor: `FindDuplicatesService.cs` had three co-located records (`FindDuplicatesOptions`, `DuplicateOccurrence`, `DuplicateGroup`) and the consumer `FindDuplicatesResult.cs` referenced `DuplicateGroup` unqualified.
- **WORKFLOW gotcha (NOT an rt bug) 2026-05-01**: A previous failed batch attempt at the Core/→Services/ refactor left untracked `Services/*Service.cs` files on disk. After `git checkout src/ tests/` reverted the tracked files, the untracked orphans survived. The next batch's `--move-file` step then hit "Target already exists" and silently skipped (the warning was real but I had filtered output via grep), leaving each file in BOTH locations. Easy to misdiagnose as a duplicate-file bug in rt. **Lesson:** after `git checkout` from a partial rt batch, always `git clean -fdn` (preview) → `git clean -fd` (execute) to remove untracked leftovers before retrying. Memorialised in `~/.claude/projects/.../memory/feedback_git_clean_after_checkout.md`.
- 2026-05-01: **`rt refactor move --type` does not add `using` directives for sibling-type references in the moved file**. Reproducer: `rt refactor move --type "RoslynTools.Core.MakeSealedService" --to-namespace "RoslynTools.Services" --solution RoslynTools.slnx` on a type that uses sibling types from its old namespace (`SolutionWriter`, `SymbolDocumentLocator`, `RtConsole`, `RtOutputContext`, `RtLog`) — namespace declaration is updated, but the moved file now fails to compile with CS0103 for every sibling reference because the old namespace's implicit-scope coverage is gone. Dry-run also misreports — claimed 1 file modified, but in practice the moved file needs `using <old-namespace>;` added, and any consumer that referenced the moved type unqualified via the old namespace's implicit scope needs a new `using <new-namespace>;` too. Fix: in `MoveCommand` single-type path, after `Renamer` updates the type's namespace, walk the moved document's `IdentifierNameSyntax` nodes, resolve via `SemanticModel`, and for any symbol whose containing namespace is the old namespace (and is not now imported), insert `using <old-namespace>;`. Surfaced during Core/ reorg tracer-bullet session 2026-05-01.

Two regression tests added to `tests/RoslynTools.Tests/Mutation/MoveIntegrationTests.cs` — one for moved-file old-namespace using, one for consumer new-namespace using. Re-running the original reproducer (`rt refactor move "RoslynTools.Core.MakeSealedService" --to-namespace "RoslynTools.Services"`) now updates 2 files and the build is green without manual fixup.

## extract-method --replace-duplicates known issues (US-016, 2026-04-19)

- `MethodExtractorDuplicates.ReplaceDuplicatesAsync` computes the match list once up-front against the extracted solution, then mutates the solution per-match by line-range selection. When multiple matches live in the same file, later line ranges can drift as the file is rewritten; `SelectStatementsInRange` may then pick the wrong statements. Fix: either (a) process matches file-by-file bottom-up so earlier edits don't affect later line numbers, (b) re-run `FindMatchesAsync` after each replacement, or (c) carry the exact match node set from `PatternMatcher` through to replacement via `SyntaxAnnotation`.
- `ExtractMethodCommand.SetHandler` lambda is ~40 lines, exceeding the "Command ExecuteAsync ≤ 20 lines" thin-shell rule introduced by this PRD. Fix: extract an `ExtractMethodHandler.RunAsync(ctx)` helper in Core.

# Report C# language-feature usage and density

## Context

`rt` can report complexity and specific code smells, but it cannot answer which C#
language features a solution actually uses or how concentrated those features are.
That makes modernization work depend on text searches that conflate tokens with
language constructs and provide no stable denominator.

The proposed command is:

```text
rt analyze language-features --solution RoslynTools.slnx
```

“All language features” means all entries in an explicit, versioned rt feature
catalogue. It must not imply that Roslyn exposes an exhaustive built-in feature list.
Each detector records a stable ID, category, first C# version, counting rule, and
whether it is syntax-, semantic-, or project-option-based.

Density has two distinct meanings and the result must not blur them:

- universal density: occurrences per 1,000 non-generated source lines and percentage
  of analyzed files containing the feature;
- adoption: feature occurrences divided by a mechanically valid opportunity set,
  such as file-scoped namespaces divided by namespace declarations. Features without
  a defensible opportunity denominator omit adoption rather than inventing one.

Captured from feedback item `FB-374` and the protocol in
`ralph/sessions/2026-08-27-language-feature-density.md`.

## Acceptance Criteria

- [x] `rt analyze language-features` is a read-only, daemon-preferred analyze command
      with one host-neutral definition and typed application port projected through
      the generic CLI and MCP adapters after US-143 lands.
- [x] The typed result declares `catalogVersion`, analyzed projects/files/non-generated
      source lines, project language versions, diagnostics, and one row per detected
      catalogue feature.
- [x] Every feature row has a stable ID, display name, category, first C# version,
      counting basis, occurrence count, files count, occurrences per KLOC, and file
      percentage.
- [x] A feature includes an adoption numerator, denominator, label, and percentage only
      when the detector has a mechanically valid opportunity set.
- [x] Syntax-only, semantic, and project-option features are distinguished. C# syntax
      is not conflated with runtime/library API usage.
- [x] Generated/intermediate documents and `<auto-generated>` sources are excluded by
      default; `--include-generated` opts in and the result states the policy used.
- [x] `--feature <id>`, `--category <name>`, `--introduced-since <version>`, `--top <n>`,
      and `--include-locations` provide deterministic filtering and drill-down without
      changing how metrics are calculated.
- [x] Locations are omitted by default to keep CLI/MCP payloads bounded; when requested,
      each occurrence carries project, path, line, and column.
- [x] Solution totals and per-project rollups use the same feature IDs and definitions.
- [x] Unloadable projects, parse failures, and unsupported syntax produce typed partial-
      analysis diagnostics; the command never silently reports zero for an unanalysed
      project.
- [x] Catalogue contract tests pin IDs/counting rules, focused detector tests cover
      representative C# versions, and CLI/MCP/daemon parity tests prove identical data.
- [x] Suggested refactors are emitted only for deterministic mappings to existing rt
      commands; an observed feature is not itself labelled a problem.

## Explicitly out of scope

- Automatically rewriting the project to adopt newer language features.
- Ranking language features as inherently good or bad.
- Counting framework or BCL API usage as C# language syntax.
- Historical trend comparison or a checked-in baseline in the first slice.

## Decision log

| Date | Decision | Rationale |
|---|---|---|
| 2026-08-27 | Use a versioned catalogue with stable IDs | “All” otherwise becomes untestable and changes silently with the compiler package. |
| 2026-08-27 | Report both KLOC/file density and optional opportunity adoption | Raw density compares unlike constructs poorly; adoption is useful only where its denominator is rigorous. |
| 2026-08-27 | Defer implementation until US-143 | A new command should not add another entry to the transitional daemon catalogue or create CLI/MCP coupling debt. |
| 2026-08-27 | Keep refactoring suggestions advisory | Candidate locations are mechanically detected, but edits require semantic/API/control-flow review and are never presented as automatic. |

## Resolution

Implemented `rt analyze language-features` as a host-neutral, daemon-preferred typed
operation shared by CLI and the generic MCP adapter. Catalogue `csharp-v1` contains 60
stable entries spanning syntax, semantic, and project-option detector shapes. The 53
entries supported by the pinned Roslyn compiler are analyzed; seven C# 15 entries emit
typed `unsupported_detector` diagnostics instead of false zero counts.

The refactoring view is available through `--refactorable-only --include-locations`.
It reports explicit, non-automatic review candidates for block-scoped namespaces,
set accessors, and switch statements while retaining the aggregate adoption metrics.

Verification on 2026-08-27:

- Release build: 0 warnings, 0 errors.
- Tests: 1,643 passed and 9 skipped in the CLI/core project; 61 passed in MCP.
- Format verification and diff/JSON checks passed.
- Scoped coverage: 82.33% line, 78.99% branch, 97.18% method.
- No mutation score is claimed: the repository Stryker mutate globs combined with the
  scoped CLI filter and selected unrelated `MethodExtractor` mutants, whose safe-mode
  compile failure prevented a valid feature-specific report.
